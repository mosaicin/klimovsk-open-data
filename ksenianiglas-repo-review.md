# Обзор открытых репозиториев ksenianiglas

## Что можно применить

Из `mapping_estonia` применимы идея явного указания источника геоданных и раздельных скриптов по тематическим слоям. Для маршрута улицы Ленина это означает разделять адресный, дорожный, инфраструктурный и закупочный слои и сохранять источник каждого слоя.

Из `Tallinn_population_density` применимы пространственное объединение геометрии с таблицей показателей и расчёт производной метрики после `left_join`. Для ЕИС аналогом будет объединение географического/адресного слоя с реестром контрактов только после нормализации адресов и фиксации уровня совпадения.

Из `lastfm` и `facebook_message_stats` применим общий ETL-подход: получить исходные данные, очистить поля, сгруппировать и построить агрегаты. Этот подход переносится на расчёт числа процедур по заказчику, частоты побед, повторяемости пар и ценовых снижений.

Из `tennis_stats` применимы функции для повторного расчёта производных показателей и последовательная агрегация по объекту анализа. Для закупок это означает отдельные функции расчёта снижения цены, времени между ставками и статистики по процедурам.

## Что не переносится напрямую

Код использует разные внешние источники, локальные файлы, R-пакеты и иногда персональные данные. Его нельзя копировать в рабочий ETL без адаптации, лицензий, проверки актуальности источников и удаления персональных данных. Репозитории профиля не содержат готового Airflow/cron или SQL-пайплайна ЕИС.

## Предлагаемая интеграция

В `klimovsk-open-data` следует добавить:

- адаптер новых CSV/XML-файлов ЕИС в staging;
- checksum-манифест обработанных файлов;
- идемпотентный запуск PostgreSQL ETL;
- отдельные агрегаты для закупок, адресов, участников и индикаторов;
- картографический экспорт только на основе подтверждённых адресов;
- cron и Airflow варианты запуска с блокировкой параллельных запусков.
