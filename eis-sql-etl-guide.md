# SQL ETL для сырых выгрузок ЕИС

## Архитектура

Процесс делится на четыре слоя: сырые файлы, staging-таблицы, нормализованные таблицы и аналитические views. Сырые значения в staging хранятся как `TEXT`, потому что ЕИС и агрегаторы могут использовать разные форматы дат, десятичные разделители и пустые значения. Преобразование выполняется только при загрузке в нормализованный слой.

## Порядок запуска

1. Создайте базу PostgreSQL и выполните `eis_etl_postgres.sql`.
2. Создайте запись в `eis.load_batches` для каждого файла и сохраните SHA-256 источника.
3. Загрузите CSV/XML-преобразование в соответствующую таблицу `eis_stg.*` через `COPY` или `\copy`.
4. Проверьте количество строк и `eis.load_errors`.
5. Выполните INSERT-блоки ETL в транзакции.
6. Запустите проверки ссылочной целостности, дублей и пропусков.
7. Только после проверки стройте аналитическое представление и рассчитывайте индикаторы.

Пример загрузки CSV:

```sql
INSERT INTO eis.load_batches(source_file, source_sha256, row_count)
VALUES ('procurements_2026.csv', '[sha256]', 0)
RETURNING batch_id;

\copy eis_stg.procurements_raw(batch_id, procurement_id, ikz, law,
  procurement_method, customer_inn, customer_name, subject, okpd2,
  published_at, nmck, region, source_document_id)
FROM 'procurements_2026.csv' WITH (FORMAT csv, HEADER true, NULL '');
```

В реальном запуске замените `[sha256]`, путь и состав полей на фактические данные. Если выгрузка ЕИС имеет другое имя поля или вложенную структуру, сначала создайте промежуточный адаптер, а не изменяйте исходные файлы.

## Дедупликация

`procurement_id`, `contract_id` и `bid_id` используются как ключи при `ON CONFLICT`. Повторная загрузка того же файла обновит запись, а не создаст дубликат. Однако перед обновлением следует проверить, что новая запись действительно новее или содержит более полный документ. Для аудита сохраняйте `source_batch_id` и `source_document_id`.

Если два источника противоречат друг другу, не перезаписывайте значение молча. Сохраните оба источника в отдельной таблице документов и создайте запись в журнале конфликтов. Для юридически значимого анализа приоритет имеет официальный документ ЕИС, но даже его изменения должны сохраняться исторически.

## Преобразование полей

ИНН и ОГРН очищаются от пробелов и нецифровых символов, но остаются строками. Даты преобразуются в `timestamptz` или `date` только после проверки. Суммы преобразуются из русских форматов с запятой и пробелами в `numeric(18,2)`. Некорректные строки не должны превращаться в ноль: их нужно направлять в `eis.load_errors`.

## Минимальные проверки после загрузки

```sql
-- Контракты без найденной процедуры
SELECT c.contract_id
FROM eis.contracts c
LEFT JOIN eis.procurements p USING (procurement_id)
WHERE c.procurement_id IS NOT NULL AND p.procurement_id IS NULL;

-- Ставки без участника или времени
SELECT * FROM eis.bids
WHERE participant_inn IS NULL OR submitted_at IS NULL OR price IS NULL;

-- НМЦК и цены, требующие ручной проверки
SELECT procurement_id, nmck
FROM eis.procurements
WHERE nmck IS NULL OR nmck <= 0;

-- Возможные дубли источников
SELECT source_document_id, COUNT(*)
FROM eis.documents
WHERE source_document_id IS NOT NULL
GROUP BY source_document_id
HAVING COUNT(*) > 1;
```

Проверки не исправляют данные автоматически. Каждую ошибку нужно классифицировать как пропуск, ошибка формата, конфликт источников или отсутствие документа.

## Практические ограничения

SQL не может восстановить отсутствующие в публичной выгрузке цены заявок, точные временные метки или технические логи электронной площадки. Он только организует полученные данные. Технические признаки IP, сессий, устройств и электронных подписей должны загружаться отдельным законно полученным источником, с ограничением доступа и журналом происхождения.

Не загружайте в публичный GitHub банковские реквизиты, персональные данные, закрытые журналы ЭТП или сырые документы с ограниченным доступом. В репозитории храните DDL, ETL, обезличенные образцы и публичные ссылки; закрытые данные должны оставаться в защищённом хранилище.
