# Перестановочный тест синхронности подачи заявок на Python

## Идея теста

Для каждой закупки берутся точные временные метки подачи заявок или ценовых шагов. Наблюдаемая статистика — доля пар ставок разных участников, поданных не дальше заданного порога `Δ` секунд друг от друга.

Нулевая гипотеза: при сохранении общего набора временных меток и числа ставок каждого участника метки участников могли быть распределены случайно. Альтернативная гипотеза: события разных участников необычно часто оказываются близко по времени.

Тест не доказывает наличие соглашения. Малое p-value означает, что наблюдаемая временная близость необычна относительно выбранной нулевой модели.

## Формат входного CSV

Скрипт ожидает минимум три столбца:

```csv
procurement_id,participant_id,submitted_at
A-001,INN_A,2020-04-01T10:00:00+03:00
A-001,INN_B,2020-04-01T10:00:03+03:00
A-001,INN_A,2020-04-01T10:05:00+03:00
A-001,INN_B,2020-04-01T10:05:20+03:00
```

В реальном анализе строки должны быть получены из официальных протоколов или оригинальных журналов площадки. Не следует восстанавливать время по округлённым данным или по порядковому номеру ставки.

## Запуск

```bash
python3 permutation_test_sync.py bids.csv \
  --delta-seconds 5 \
  --permutations 10000 \
  --seed 20260815 \
  --out permutation_sync_results.json
```

Параметр `--delta-seconds` задаёт временное окно. Его следует определить до просмотра результата или заранее проверить несколько технически обоснованных порогов, например 1, 5 и 30 секунд.

`--permutations` — число перестановок. Для рабочего скрининга можно использовать 10 000 или больше; для публикации необходимо зафиксировать seed и число перестановок.

## Что делает скрипт

1. Разбирает временные метки в UTC.
2. Разделяет данные по `procurement_id`, поэтому ставки разных закупок не смешиваются.
3. Считает наблюдаемую долю близких пар ставок разных участников.
4. Перемешивает только метки участников внутри закупки. Общие временные метки и число ставок каждого участника сохраняются.
5. Повторяет расчёт заданное число раз и строит нулевое распределение.
6. Рассчитывает верхнее эмпирическое p-value с поправкой add-one:

```text
p = (1 + число перестановок со статистикой >= наблюдаемой) / (B + 1)
```

7. Сохраняет среднее, стандартное отклонение и 2,5/97,5% квантили нулевого распределения.

## Как интерпретировать результат

| Результат | Корректная интерпретация |
|---|---|
| p-value не мало | данных недостаточно, чтобы считать временную близость необычной относительно нулевой модели |
| малое p-value | наблюдаемая близость необычна в рамках выбранной модели; нужен документальный и технический follow-up |
| малое p-value при одном пороге | результат чувствителен к выбору окна; нужны анализ устойчивости и контрольные группы |
| малое p-value только для одной закупки | возможен локальный эффект; нельзя обобщать на весь портфель |
| малое p-value после просмотра десятков пар и порогов | нужна поправка на множественные проверки и публикация полного набора тестов |

## Обязательные проверки устойчивости

Тест нужно повторить с несколькими заранее обоснованными окнами, с контрольной группой закупок на той же площадке и в сопоставимый период, а также после исключения процедур с неполными журналами. Для 232 контрактов следует отдельно учитывать площадку, способ закупки, число участников, предмет, регион, НМЦК и техническое разрешение временных меток.

При большом числе участников полезно считать результат отдельно для каждой пары и использовать поправку Benjamini–Hochberg для контроля FDR. Нельзя публиковать только наиболее «подозрительную» пару, не показывая все проверенные пары.

## Важные ограничения

Одинаковая временная метка может возникнуть из-за округления, пакетной обработки, автоматических уведомлений, общего регламента площадки, корпоративной сети, прокси, VPN или общего представителя. Поэтому IP, устройство или временная близость являются индикаторами, а не доказательством соглашения.

Перестановочная модель предполагает, что при нулевой гипотезе метки участников можно обменивать внутри конкретной закупки. Если участники имеют разные технические задержки, разные лимиты или разные правила доступа, эта предпосылка может быть нарушена. В таком случае нужна более реалистичная блокированная перестановка: внутри площадки, временного окна, этапа процедуры или другой заранее определённой страты.

В текущем репозитории отсутствует полный журнал ставок по 232 контрактам, поэтому скрипт пока проверен только на синтаксис и CLI, а не на фактическом результате по этому массиву. Запуск по реальным данным следует выполнять после получения оригинального CSV из ЕИС/оператора площадки.

## Файл скрипта

`permutation_test_sync.py` сохраняет результаты в JSON и не генерирует фиктивные закупочные данные. Он требует реальный CSV с временными метками.
